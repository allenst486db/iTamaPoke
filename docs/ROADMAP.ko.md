## A. 이로치 2단계 — UI

1단계(스프라이트 386종 생성)는 완료됐고, 게임 로직도 원래부터 완성돼 있었습니다.
남은 건 **이미 있는 상태를 화면에 더 보여주는 일**뿐이라, 아래 넷은 서로
독립적입니다. 원하는 것만 골라서 넣으면 됩니다.

### A-1. 도감 상세 화면에 노멀/이로치 토글

현재 `renderGalleryDetail`은 `pet.isShinyRegistered(dex)`가 참일 때만 이로치
초상화를 그립니다. 즉 **이로치로 키워본 적이 없으면 그 종의 이로치 색을 볼
방법이 아예 없습니다.** 386종 전부 파일은 있는데 보여줄 길이 없는 상태.

- 초상화를 탭하면 노멀 ↔ 이로치 전환
- `TPSprite.load(dex:shiny:)`는 이미 양쪽을 다 불러올 수 있으므로 로더는 손댈 것 없음
- 등록 안 한 이로치를 보여줄지는 판단 필요 — "수집 스포일러"로 볼 수도 있음.
  등록된 것만 토글 허용하는 쪽이 게임 성격에 맞을 수 있음

### A-2. 도감 필터에 SHINY 추가

`PetScreen.swift`의 필터는 지금 ALL / RAISED / CAUGHT 셋(`galleryFilter` 0/1/2).
네 번째로 SHINY를 넣는 작업입니다.

- 필터 판정 함수와 필터 라벨 배열(`[pet.filterAllText, pet.raisedMarkText,
  pet.caughtMarkText]`) 양쪽에 추가
- 필터 칸이 3개에서 4개로 늘어나므로 **가로 폭 재배치 필요**
- i18n에 `S_FILTER_SHINY` 신규 문자열 1개 × 6개 언어

### A-3. 도감 헤더에 이로치 카운터

지금 헤더는 `R:x C:y`(키운 수 / 잡은 수)만 보여줍니다. `S:z`를 붙이는 일.

- `pet.h`에 `shinyCount()` 신규 — `registeredCount()` 바로 옆에 같은 모양으로,
  `dexShinyReg` 비트맵을 세면 됨. 10줄 안쪽
- `TPPet.h/.mm`에 노출, 헤더 포맷 문자열 수정
- 헤더가 길어지므로 폭 확인 필요

### A-4. BOX 이로치 표시 — **결정이 먼저 필요함**

지금 BOX에는 이로치 표시가 없습니다. 그런데 그냥 빠뜨린 게 아닙니다:

> `battle.cpp`에는 shiny라는 개념이 아예 없습니다. 야생 포켓몬은 구조적으로
> 이로치가 될 수 없고, `dexShinyReg`는 **직접 키운** 이로치만 기록합니다.

그래서 선택지가 둘입니다.

- **(a) 현행 유지** — "이로치는 알에서만 나온다"를 규칙으로 확정하고, BOX에는
  표시할 것이 없으므로 아무것도 안 함. 코드 변경 0.
- **(b) 야생에도 이로치 추가** — `battle.cpp`에 shiny 굴림과 필드 추가, 포획
  경로에서 `dexShinyReg` 기록, BOX 행에 `*` 표시. 이건 **게임 규칙 변경**이라
  다른 셋과 성격이 다릅니다. 알의 희소성(1/48~1/8, 스트릭·유대감 보정, 작별
  직후 2배)이 이로치의 유일한 획득 경로라는 설계를 바꾸는 일.

(a)를 기본값으로 두는 것을 권합니다. (b)를 하려면 A-1~A-3과 분리해서 따로.

## C. 새로 생긴 확인 사항

### C-1. 워치 스프라이트 전송 용량

`Resources/mons`가 53MB → **106MB**로 두 배가 됐습니다(파일 수 302 → 772).

`TPWatchSpriteSync.syncToWatch()`는 `TPMonsSource.documentsMonFiles`를 하나씩
`WCSession.transferFile`로 넘깁니다. 즉 **Documents 경로로 스프라이트를 넣는
사용자**는 전송량이 두 배가 됩니다. 코드 주석 자체도 "potentially tens of MB"를
경고하고 있는데, 이제 100MB대입니다.

- 실기에서 전송이 끝나는지, 중간에 실패하는지 확인 필요
- 필요하면 워치에는 이로치를 빼고 노멀만 보내는 옵션 검토
- 참고: Xcode로 직접 빌드하면 번들에 들어가므로 이 경로를 타지 않음

### C-2. 앱 용량

시뮬레이터 디버그 빌드 기준 `TamaPoke.app`이 **222MB**입니다. 실기 릴리스
빌드에서 어느 정도인지, 개인 기기 설치에 무리 없는지 확인 필요.

### C-3. 이로치 실제 부화 확인

1단계에서 한 검증은 여기까지입니다:

- 772개 파일 전수 구조 검사 (헤더·오프셋이 파일 끝까지 정확히 일치)
- 노멀을 그대로 복사한 이로치 0건
- 앱과 같은 리더 로직으로 프레임 디코딩 → 나무지기 청록, 브케인 주황 확인

**게임 안에서 2-3세대 이로치가 실제로 부화하는 장면은 확인하지 못했습니다.**
확률이 1/48이라 우연에 맡기기 어렵습니다. 로더 경로 자체는 1세대 이로치로
이미 동작이 확인된 코드 그대로지만, 굳이 확인하려면 임시로 확률을 1/1로
바꿔서 한 번 돌려보는 방법이 있습니다.

### C-4. 12종의 이로치 애니메이션 부족

16, 26, 161, 171, 191, 203, 225, 274, 327, 341, 346, 361은 이로치 시트에 Eat / Sit /
Pose / Nod / Breath 일부가 없습니다. SpriteCollab 원본 데이터 사정이고, 그리는
쪽이 전부 `has()`로 막고 Idle로 폴백하므로 **조치 불필요**입니다. 나중에
"이로치일 때 먹는 모션이 없네"를 버그로 다시 조사하지 않도록 기록만 해둡니다.

## E. 다형(폼 체인지) 포켓몬 — 안농 서브도감 등

2026-08-27 대화에서 나온 아이디어: 안농(Unown, #201)의 28개 폼(A~Z, `!`, `?`)을
모으는 별도 서브도감 화면. 구조를 확인해보니 **이번 사운드/에셋 작업과는 규모가
다른 독립 기능**이라 따로 적어둡니다.

- 이 앱은 종을 `speciesId`(도감번호) 하나로만 관리합니다 — `Pet`에 "같은
  도감번호, 다른 겉모습(폼)"이라는 필드가 아예 없고, 이로치도 별도 `bool`
  플래그 하나일 뿐입니다.
- 1~3세대에는 안농 말고도 캐스퐁(날씨 폼)·테오키스(4폼)처럼 원래 다형인 종이
  이미 들어있는데, `dex.h`를 보면 **이 둘도 그냥 단일 고정 모습으로만
  존재**합니다. 즉 "폼이 여러 개인 종"을 다루는 인프라 자체가 프로젝트 어디에도
  없다는 뜻 — 안농만을 위한 새 서브시스템을 처음부터 만들어야 합니다.
- 스프라이트(`p번호.bin`)·박스·도감 그리드가 전부 "도감번호 1개 = 칸 1개"
  구조라, 안농의 28폼을 담으려면 최소한 다음이 필요합니다.
  1. 폼별 스프라이트 28장 확보 (PMD SpriteCollab에 폼별로 실제 있는지 확인 먼저)
  2. 부화/포획 시 "어떤 폼이 나왔는지" 뽑는 로직
  3. 세이브 데이터에 폼 필드 추가 (세이브 포맷 변경)
  4. 안농 전용 서브 도감 그리드 화면 신규 제작 (기존 도감 그리드 재사용 불가)
- 캐스퐁·테오키스까지 같이 다형 지원을 넣을지, 안농 하나만 먼저 할지도 별도
  판단 필요.

기술적으로 불가능한 건 아니지만 규모가 있는 별도 기능 개발 건이라, 진행하게
되면 이 섹션을 시작점 삼아 전용 계획서를 새로 잡는 것을 권합니다.
