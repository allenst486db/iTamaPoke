# 한글화 가능성 검토

작성 시점: 2026-08-25 (커밋 `53f2485` 기준)

---

## 결론

**가능합니다. 다만 "문자열만 번역"으로는 되지 않습니다.**

이 포트의 화면 정렬은 전부 **"한 글자 = `size*6` 픽셀"** 이라는 고정 가정 위에
서 있습니다. 한글은 실측 **1.44배** 넓습니다. 번역 문자열만 넣으면 가운데 정렬,
우측 정렬, 줄바꿈, 자동 축소가 **한 곳도 빠짐없이** 어긋납니다.

그래서 순서가 이렇게 됩니다.

1. **폭 실측으로 정렬 산술을 교체** ← 전체 작업의 절반 이상, 그리고 선행 필수
2. 문자열 데이터 추가 (분량은 크지만 난이도는 낮음)
3. 도감 설명문 한국어 + 줄바꿈 방식 변경

1번은 한글화를 안 하더라도 단독으로 가치가 있습니다. 지금도 ASCII가 3% 어긋나
있고, 악센트가 들어간 유럽어에서는 더 어긋납니다.

## 1. 폰트와 레이아웃 — 가장 큰 난관

### 근거 (실측)

`gfxText`는 `.system(size: size*10, weight: .semibold, design: .monospaced)`로
그립니다. macOS/iOS의 같은 폰트 API로 실제 글자 폭을 재봤습니다.

| 문자열 | 실제 사용된 폰트 | size 1 기준 글자당 폭 | 코드의 가정(6.0px) 대비 |
|---|---|---|---|
| `ABCDEFGH` | AppleSystemUIFontMonospaced | 6.18px | 1.03× |
| `12345678` | AppleSystemUIFontMonospaced | 6.18px | 1.03× |
| `가나다라마바사아` | **AppleSDGothicNeo** | **8.65px** | **1.44×** |
| `체력` | AppleSDGothicNeo | 8.65px | 1.44× |
| `포켓몬 도감` | **두 폰트가 섞임** | 8.24px | 1.37× |

읽어낼 점이 셋입니다.

- **한글은 모노스페이스 시스템 폰트에 글리프가 없습니다.** Apple SD Gothic Neo로
  폴백되고, 그 폰트는 모노스페이스가 아닙니다.
- **혼합 문자열은 런마다 폰트가 다릅니다.** `포켓몬 도감`은 한글 런과 공백
  런이 서로 다른 폰트로 잡힙니다. 그래서 **문자열 단위로 상수 배율을 곱하는
  임시방편이 통하지 않습니다.** 실제로 재는 수밖에 없습니다.
- ASCII도 이미 3% 어긋나 있습니다. 지금 티가 안 나는 건 여유 폭이 그만큼
  있어서일 뿐입니다.

### 영향 범위

| 위치 | 산술 | 한글에서 벌어지는 일 |
|---|---|---|
| `gfxTextCentered` (`TPGraphics.swift:171`) | `cx - count*size*3` | 호출 **115곳**이 전부 오른쪽으로 밀림 |
| `gfxTextCentered2` (`:178`) | `x + (w - count*size*6)/2` | 버튼 라벨이 버튼 밖으로 |
| 개별 정렬 **31곳** (`PetScreen.swift`) | `count*6`, `*9`, `*12`, `*18` | 점수·게인·라벨 위치 어긋남 |
| BOX 타입 우측 정렬 | `tx = 394 - count*6` | 타입 칩이 박스 오른쪽으로 넘침 |
| 도감 설명 줄바꿈 | `Int(usableW / (size*6))` | 칼럼 수를 44% 과대 계산 → 박스 넘침 |
| 스타터 이름 축소 판정 | `count*18 <= 240` | 축소가 필요한데 안 함 |
| 설정 언어/사운드 알약 | `(w - count*12)/2` | 라벨이 알약 밖으로 |

`.count`는 Swift에서 자소 클러스터 수라 **한글 글자 수 자체는 정확히 셉니다.**
바이트 수와 헷갈리는 문제는 없습니다. 순수하게 **폭** 문제입니다.
(C쪽에서 표시 문자열에 `strlen`을 쓰는 곳은 없습니다. `Preferences.mm` 두 곳뿐이고
그건 저장값 길이라 무관합니다.)

### 해결 방법

`GraphicsContext.resolve(_:)` → `ResolvedText.measure(in:)`로 실제 폭을 재는
헬퍼를 `TPGraphics`에 하나 만들고, 위 표의 산술을 전부 그걸로 교체합니다.

```swift
func gfxTextWidth(_ s: String, _ size: Int) -> CGFloat   // 실측
```

- SwiftUI Canvas에 이미 있는 API라 새 의존성 없음
- 한 번 고치면 모든 언어가 정확해짐
- 캐싱 고려: 매 프레임 전부 재면 비용이 붙습니다. 문자열+크기 키로 캐시를
  두거나, 정적 라벨만 미리 재는 방식

### 워치에서 더 위험함

워치 화면은 폰보다 작습니다. 폰에서 겨우 들어가는 라벨이 워치에서 44% 넓어지면
잘립니다. 폰에서 통과했다고 끝난 게 아니라 **워치 실기 확인이 따로 필요합니다.**

## 2. 문자열 데이터 — 분량은 크지만 난이도는 낮음

### 번역 대상

| 테이블 | 위치 | 추가할 항목 수 |
|---|---|---|
| `STRINGS[LANG_COUNT][STR_COUNT]` | `i18n.cpp:10` | **220** |
| `MED_NAME` / `MED_LBL` / `MED_DSC` | `i18n.cpp:368/376/384` | 8 × 3 = **24** |
| `DEX_NAMES[DEX_LANG_COUNT][387]` | `dex.h:423` | **386** |
| Swift 하드코딩 | `PetScreen.swift` | **3** |
| | | **합계 633** |

### 구조 변경

- `enum Lang`에 `LANG_KO` 추가 → `LANG_COUNT` 6 → 7
- `DEX_LANG_COUNT` 6 → 7 (`dex.h:9`)
- `PetScreen.swift:772`의 `langCodes = ["ES","EN","FR","DE","IT","PT"]`에 `"KO"`
  추가 — 이건 Swift쪽에 따로 박혀 있는 배열이라 C 테이블만 고치면 놓칩니다
- 설정 화면 언어 순환은 `% langCodes.count`라 자동으로 따라옴
- 저장된 언어 인덱스는 그대로 유효 (KO를 **맨 뒤에** 추가할 경우에 한해).
  중간에 끼워넣으면 기존 사용자의 언어가 바뀝니다

### Swift 하드코딩 문자열

거의 없습니다. 실제로 번역이 필요한 건 셋뿐입니다.

- `"POKEDEX"` (`:1943`), `"POKeDEX"` (`:2012`) — 도감 머리글
- `"GEN 1/2/3"` (`:2189`) — 스타터 화면 세대 표시

나머지 하드코딩(`"Zz"`, `"?"`, `"<"`, `">"`, `"v"`, `"*"`, `"C"`, `"x3"`, `"+2"`)은
기호라 번역 대상이 아닙니다.

### 타입 이름은 언어 테이블이 아님

`kTypeNames[19]` (`TPPet.mm:644`)은 `"NORMAL"`, `"FIRE"`, `"WATER"`... 로
**영어 고정**입니다. i18n 테이블이 아닙니다.

한글화하려면 언어별 테이블로 승격시켜야 합니다. 다만 타입 이름은 원작 한국어판이
`노말`, `불꽃`, `물`처럼 **짧아서** 도감 상세의 타입 칩과 BOX 행에는 오히려
유리합니다. 선택 항목으로 두어도 됩니다.

### 기존 전제: ASCII 전용

`i18n.h:4`와 `i18n.cpp:8` 주석이 명시하고 있습니다.

> 펌웨어 비트맵 폰트에 악센트가 없어서 스페인어도 `acentos` 없이 작성했다

이 포트는 시스템 폰트로 그리므로 UTF-8이 실제로 렌더됩니다. 하지만 **테이블에
비ASCII가 들어가는 건 한글이 처음입니다.** `const char*`는 UTF-8 바이트라
저장·전달에는 문제가 없고, 위에서 확인했듯 표시 문자열에 `strlen`을 쓰는 곳도
없습니다. 다만 이 주석은 갱신해야 합니다 — 더 이상 사실이 아니게 되므로.

## 3. 도감 설명문

### 데이터는 있음

`Scripts/fetch_dex_entries.sh --lang ko`로 받을 수 있습니다. PokéAPI에 한국어가
있는지 실제로 확인했습니다.

| 도감 번호 | 한국어 이름 | ko 설명문 수 | 첫 설명문 길이 |
|---|---|---|---|
| 1 이상해씨 | 이상해씨 | 8 | 42자 |
| 25 피카츄 | 피카츄 | 12 | 37자 |
| 152 치코리타 | 치코리타 | 4 | 49자 |
| 252 나무지기 | 나무지기 | 4 | 52자 |
| 386 테오키스 | 테오키스 | 4 | 39자 |

12종을 1~386 범위에 걸쳐 표본 조사했고 **전부 한국어 이름과 설명문이
있었습니다.** 전수 확인은 아닙니다.

한국어 설명문이 영어보다 **짧습니다**(42자 안팎, 표본 33~52자). 축소 로직에는 유리합니다. 다만
글자당 폭이 1.44배라 실제 차지하는 폭은 비슷하거나 조금 넓습니다.

스크립트의 줄바꿈·공백·소프트하이픈 정규화는 이미 들어있어 그대로 씁니다.

### 줄바꿈 알고리즘은 바꿔야 함

`TPDexEntryText.wrap(_:columns:)`는 **greedy word wrap**입니다. 공백으로 단어를
쪼개고, 한 글자 = 한 칼럼으로 셉니다. 한국어에는 둘 다 안 맞습니다.

- 칼럼 수를 폭 기준으로 다시 계산해야 함 (1번 항목의 실측 헬퍼가 여기에도 필요)
- 한국어는 공백 없이 이어지는 구간이 길어 단어 단위 줄바꿈이 잘 안 걸립니다.
  현재의 "한 줄보다 긴 단어는 강제 분할" 폴백이 계속 발동해서 어색하게 끊깁니다
- **글자 단위 줄바꿈**으로 바꾸는 게 맞습니다. 한국어 조판은 원래 그렇게 합니다.
  다만 여는 괄호 뒤나 닫는 괄호·마침표 앞에서 끊기지 않게 하는 정도의 금칙
  처리는 있으면 좋습니다

## 4. 작업 순서

의존 관계 때문에 순서를 바꾸기 어렵습니다.

1. **폭 실측 헬퍼 + 정렬 산술 교체** — 선행 필수. 한글화 없이도 단독 가치.
   가장 큰 덩어리이고, 회귀 위험도 여기 집중돼 있습니다 (115 + 31 곳)
2. **`LANG_KO` 추가** — enum, `LANG_COUNT`, `DEX_LANG_COUNT`, `langCodes`
3. **문자열 633개** — UI 220 + 메달 24 + 도감 이름 386 + Swift 3.
   도감 이름은 PokéAPI에서 스크립트로 뽑을 수 있으므로 실제 손번역은 247개
4. **도감 설명문** — `--lang ko` 페치 + 글자 단위 줄바꿈
5. **타입 이름 언어화** (선택)
6. **검증** — 폰·워치 양쪽 실기. 워치가 진짜 관문

## 5. 리스크

- **워치 화면 폭** — 위에 적은 대로. 폰에서 통과해도 워치에서 잘릴 수 있음
- **회귀 범위** — 정렬 산술 146곳을 건드리는 작업이라, 한글을 안 켜도 기존 6개
  언어 화면이 전부 영향권입니다. 언어별 스크린샷 비교가 필요
- **저작권** — 포켓몬 한국어 이름과 설명문도 영어판과 똑같이 닌텐도/게임프리크
  자산입니다. 스프라이트·도감 설명문과 **동일하게 취급**해야 합니다: 커밋 금지,
  gitignore 유지, 사용자별 페치. `DEX_NAMES`에 386개 한국어 이름을 직접 박아
  넣는 건 지금 영어·독일어 이름이 이미 소스에 들어있는 것과 같은 상태가 되므로,
  현행 방침(`NOTICE`의 예외 조항)과 어긋나지 않는지 확인이 필요합니다
